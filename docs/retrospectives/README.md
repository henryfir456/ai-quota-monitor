# 每輪開發回顧（Development Retrospective）

## 目的
每輪有實際程式、規範、部署或驗證異動後，在交付前整理阻礙、根因與後續改良，減少 Agent 重複犯錯。這是事實紀錄，不可用回顧取代必需的測試或獨立審閱。

## 寫入時機與位置
- 每輪修改交付時建立或更新 `docs/retrospectives/YYYY-MM-DD-<issue-or-task>.md`，相同任務後續修復請在同一檔增加輪次，避免重複檔案。
- 無阻礙也須寫「無」，不可省略；與其虛構根因，應標示 UNKNOWN / 待驗證。
- 回顧應在提交 PR 前完成，並於 PR 說明中連結。已經合併後才發生的人工實測結果，追加到同一記錄或新 Issue。
- 開工時先搜尋近期回顧中的同類錯誤，優先套用已驗證的預防措施；不要盲目套用不同平台的解法。
- 禁止寫入憑證、個資、客戶資料、完整敏感 Log；證據以可安全分享的路徑、命令、摘要或 URL 表示。

## 改善項目分流
- **立即修正**：在本輪授權範圍內、有必要且不擴張風險，修改後重新驗證。
- **後續 Issue**：可重現的缺陷、安全風險、跨專案共通規範缺口、需要獨立追蹤的高價值改善；先搜尋現有 Issue，避免重複，連結回顧與驗收條件。
- **規範改進**：反覆發生且根因明確，更新對應標準或測試（變更須另經審閱）；單次推測不得直接升級成全域強制規則。
- **不採用／觀察**：效益不足、根因不明或超出授權；紀錄原因，不自動開 Issue。
- 回顧本身不是 DONE 的替代品；阻塞仍須遵循現有 Gate、三輪上限、權限與部署限制。
